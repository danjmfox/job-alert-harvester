# Refusal codes

Doc type: Reference

This list was generated by reading the refusal enums in `src/` as of commit e7e0dd0 (`git rev-parse --short HEAD`). Sources: `src/core/sheets-refusals.mjs` (`SheetsRefusal`, `DriveRefusal`, `ImportRefusal`, `BuildRefusal`, `AuthTargetRefusal`), `src/core/oauth.mjs` (`AuthRefusal`, `TokenRefusal`, `CredentialRefusal`), `src/core/retry-policy.mjs` (`RetryRefusal`), `src/core/endpoints.mjs` (`EndpointRefusal`), `src/core/gmail-message.mjs` (`MessageRefusal`), `src/core/coverage.mjs` (`CoverageRefusal`), `src/adapters/gmail-api-source.mjs` (`SourceRefusal`), `src/adapters/raw-spill-source.mjs` (`SpillRefusal`), `src/adapters/ledger-store.mjs` (`LedgerRefusal`), `src/adapters/message-cache.mjs` (`CacheRefusal`), `src/adapters/xlsx-target-sheet.mjs` (`TargetRefusal`), `src/cli/fetch-loop.mjs` (`FetchRefusal`), `src/core/update-plan.mjs` (`UpdateRefusal`), `src/adapters/run-lock.mjs` (`LockRefusal`), `src/core/install-plan.mjs` (`InstallRefusal`), and `src/core/slim.mjs` (`QuarantineReason`). Regenerate it after any change to those enums.

Meanings are read from the code that raises each refusal. "Usual cause" entries are inferred from that code unless a decision record or a live run names the cause.

A refusal prints on stderr as `<code>` or `<code>: <detail>` and the command exits with status 1. Messages never contain a credential value. The commands are described in [cli.md](cli.md).

Some errors have no code and are not listed here: missing required options, `harvest build: ...` messages for an empty cache, or `--merge` and `--out` naming different files, `harvest: --in ...` messages, and raw operating-system errors. Those are in [cli.md](cli.md) and the how-to guides.

## Credentials: `gmail.credential-*` and `sheets.credential-*`

The two namespaces behave identically. `gmail.*` applies to `client.json` and `token.json`; `sheets.*` applies to `client.json` and `sheets-token.json`.

| Code | Meaning | Usual cause | What to do |
|---|---|---|---|
| `gmail.credential-missing`, `sheets.credential-missing` | The credential directory, `client.json`, or the token file does not exist. | Setup not done, or `auth` not run for this profile. | Follow [Set up Google Cloud credentials](../how-to/set-up-google-cloud.md). |
| `gmail.credential-invalid`, `sheets.credential-invalid` | A credential path is a symlink or the wrong kind of entry, or the JSON is unreadable or has the wrong shape. | A Web-type client file (no `installed` object), a hand-edited token, or a symlink. | Download a Desktop client again, or run `auth` again. |
| `gmail.credential-permissions`, `sheets.credential-permissions` | The directory mode is not exactly 0700, or a file has a group or other permission bit. | Default umask, or files copied from elsewhere. | `chmod 700` the directory and `chmod 600` each file. |

## Update: `update.*` and `lock.*`

Raised by `update`. The sequence and its output are in [cli.md](cli.md). `update.stage-failed` is the last line on stderr of every failed run, and it carries the code of the error that stopped the stage.

| Code | Meaning | Usual cause | What to do |
|---|---|---|---|
| `update.no-baseline` | The ledger holds no covered day for `linkedin` and `--from` was not given. The message reads `no fetched days to start from; run harvest fetch --from <day> first`. Nothing was fetched or built. | A first run, or a deleted ledger. | Run `fetch --from <day> --to <day>` once, or run `update --from <day>`. |
| `update.stage-failed` | A stage stopped the run. The line reads `update.stage-failed: <stage> stopped at <code>: <detail>`. The stage is `lock`, `plan`, `fetch` or `build`; `plan` is a `--dry-run` that could not read the ledger. ` at <code>` is absent when the error carries no code. No summary line was printed. | Any refusal or error of that stage. | Read `<code>` in this page and follow its entry. |
| `update.stage-failed` (stage `build`) | As above, with `; the fetch is kept, run update again` at the end. The days the fetch committed stay committed. | A build refusal after a good fetch, such as `sheets.not-imported` or a Sheets refusal. | Fix the cause of `<code>`, then run `update` again. |
| `update.stage-failed` (stage `fetch`) | The fetch stopped before the build. The build did not run. Days committed before the failure stay committed, and the next run resumes. | A Gmail or credential refusal (`gmail.reauth-required`, `gmail.quota-exhausted`, `gmail.sender-matches-nothing`), or `ledger.unreadable`. | Follow the entry for `<code>`, then run `update` again. |
| `update.stage-failed` (stage `plan`) | A `--dry-run` could not read the ledger. It prints no preview line and runs no build preview. | `ledger.unreadable`. | Follow the entry for `ledger.unreadable`. |
| `update.stage-failed` (stage `lock`) | The lock file or `.cache/` could not be used. No fetch or build ran. | `lock.unreadable` or `lock.not-writable`. | Follow the entry below. |
| `update.already-running` | Another update holds `.cache/update.lock` and its process is alive. The message reads `another update holds .cache/update.lock; wait for it to finish`. Nothing was fetched or built. | A previous run, scheduled or by hand, is still going. | Wait for it to finish. A `--dry-run` is not refused. |

The inner codes of the `lock` stage. They appear only inside `update.stage-failed`, never alone.

| Code | Meaning | Usual cause | What to do |
|---|---|---|---|
| `lock.unreadable` | The lock file cannot be read, or does not hold a process id as decimal digits, or the start-up check could not tell a live holder from a dead one. | A hand edit or damage. | Delete `.cache/update.lock` once no update is running, then run `update` again. |
| `lock.not-writable` | `.cache/` cannot be created or written, or the lock file cannot be created there. | Permissions, a file where the folder belongs, or a wrong working directory. | Fix permissions or run from the repository root. |
| `lock.held` | Another process holds the lock. Raised inside the lock adapter and reported as `update.already-running`. | As `update.already-running`. | As `update.already-running`. |

A lock left by a process that has died is not a refusal: the next run detects it, replaces it and continues.

## Install: `install.*`

Raised by `install`, `uninstall` and `status`. The commands and their output are in [cli.md](cli.md). The detail after the code is part of the stderr line `install.<code>: <detail>`. A refusal before any write leaves stdout empty. The one exception is `install.launchctl-failed` after `install --load`, which comes after the plan was printed and the files were written.

| Code | Meaning | Usual cause | What to do |
|---|---|---|---|
| `install.unsupported-platform` | The platform is not macOS. Raised by `install`, `uninstall` and `status`. The detail reads `<platform> (launchd is macOS only)`. | Running on Linux or Windows. | None: launchd exists only on macOS. |
| `install.invalid-time` | `--at` is not `HH:MM` with two digits each, hour `00`-`23`, minute `00`-`59`. The detail is the text given. A bare `--at` is `cli.missing-value`. | `5:30`, `24:00`, `05:60` or a non-time. | Write the time as `HH:MM`, for example `05:30`. |
| `install.wrong-directory` | The working directory does not hold the script that is running. The detail reads `<root> is not the checkout this harvest runs from`. | `install` run from a subdirectory or another folder. | Run it from the repository root of this checkout. |
| `install.not-on-main` | The checkout is not confirmed to be on `main`. The detail is the branch name, `detached at <commit>`, or `not a git checkout (or git cannot be run)`. | A feature branch, a detached HEAD, a copy without `.git`, or `git` missing from `PATH`. The scheduled job runs whatever the checkout holds, so a branch in progress would run unreviewed code. | Switch the checkout to `main`, or pass `--allow-any-branch`. A checkout whose `main` has no commit is not specified. |
| `install.foreign-plist` | A plist exists at the install path without the generated marker comment. The detail is its path. Raised by `install` and `uninstall`. | A plist written by hand. | Back the file up and pass `--force`, or remove it by hand. |
| `install.other-checkout` | The plist at the install path carries the marker but its `WorkingDirectory` is a different checkout. The detail reads `<plist> runs <directory>`. Raised by `install`. | `install` was run from a second clone. | Run `uninstall` from the checkout the plist runs, or pass `--force` to take the job over. `uninstall` from a different checkout is not specified. |
| `install.unsafe-path` | The checkout, the home directory or the node path cannot be embedded safely: it is relative, or holds a control character or a newline. The detail is the path as a JSON string. | An unusual folder name, or a relative `PATH` entry. | Move the checkout, or fix `PATH`. |
| `install.not-writable` | One of the three folders (`.cache/launchd/`, `.cache/logs/`, `~/Library/LaunchAgents/`) cannot take a file, so nothing was written; or `uninstall` could not remove a file. The detail reads `<path> (<system error code>)`. | Permissions, a file where a folder belongs, or a read-only volume. | Fix the permissions or the path, then run the command again. |
| `install.launchctl-failed` | A `launchctl` call failed, or the job was not loaded after `bootstrap`. The detail names the command and what it did, such as `exited <status>: <last stderr line>`. After `install --load` the written files stay. After `uninstall` a failed bootout leaves both files in place. | No login session for the user (`gui/<uid>`), a plist `launchd` rejects, or a bootout that could not stop the job. | Read the detail, fix the cause, then run the command again. `status` shows what is loaded. |
| `install.unrecognised-output` | Raised by `status`. The job is loaded, but the text of `launchctl print` yields none of `state`, `runs`, `last exit code` or `pid`. The detail reads `<command> printed nothing this harvest understands`, and the first 20 lines of that text print on stderr before it. | A change in the `launchctl print` format. | Report it with the printed lines. |

## Command line: `cli.*`

These are raised before any command does any work, so a refused command has read and written nothing.

| Code | Meaning | Usual cause | What to do |
|---|---|---|---|
| `cli.unknown-option` | An option the subcommand does not have. The message lists the valid options and, where one is close, a hint. | A misspelt flag (`--dryrun`, `--dry_run`), a short form (`-n`), or `--name=value`. | Use the spelling in the message. Options are listed in [cli.md](cli.md). |
| `cli.unexpected-argument` | A bare word where only options are allowed. | A misspelt subcommand, a value after a flag (`--dry-run file`), or a stray word. | Remove it, or correct the subcommand name. |
| `cli.duplicate-option` | The same option given twice. | A copy-and-paste error. | Give each option once. |
| `cli.invalid-date` | A date option is not a real `YYYY-MM-DD` calendar day. The message names the option and the offending text. For `ingest --window`, each end of `<from>..<to>` is checked. | A typo (`2025-012-01`), a day that does not exist (`2026-02-31`), a month past 12, a missing zero (`2026-2-1`) or a non-date. | Write a real day as `YYYY-MM-DD`. |
| `cli.missing-value` | An option that needs a value has none. | `--merge --dry-run`, a trailing `--out`, or a bare `--target`. | Add the value. |

## Quarantine reasons: `slim.*`

These are not refusals and do not stop a command. They print as `quarantined <id> (<reason>)`, the message is not cached, and its day is still committed.

| Reason | Meaning | Usual cause | What to do |
|---|---|---|---|
| `slim.body-too-short` | The plain-text body is under 1024 characters. | A truncated payload. | Inspect the message in Gmail; none is retried automatically. |
| `slim.no-advert-link` | The body has no `/jobs/view/` link. | A non-digest message, or a changed email layout. | As above. |
